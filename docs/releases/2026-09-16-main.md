# Main release verification — 2026-09-16

## Release branch and merge policy

PR #14 promotes `chore/release-dev-to-main` into `main`. Its reconciliation
merge commit has parents `32562ac` (main) and `a4a8ec6` (dev), preserving both
histories after the earlier squash promotion. Use **Create a merge commit** for
this PR and future long-lived `dev -> main` promotions, not squash/rebase merge.
Short-lived feature PRs into dev can still use squash.

The release also fixes nullable PostgreSQL feed parameters and upgrades both
Flyway modules together within major 11. PostgreSQL represents repeated HQL
parameters as independent bind slots: a null used only by `IS NULL` has no
inferred type, and nullable search concatenation could bind as `bytea`.
Explicit casts now type those guards and search expressions. Timestamp casts
are only used by null guards; actual pickup comparisons retain Instant binding.

Flyway 11.7.2 warned that PostgreSQL 18 was newer than its tested support range.
The [11.20.3 PostgreSQL module](https://github.com/flyway/flyway/blob/flyway-11.20.3/flyway-database/flyway-database-postgresql/src/main/java/org/flywaydb/database/postgresql/PostgreSQLDatabase.java)
supports major 18. No Java, Spring Boot, Flyway or database major version was
changed by this release fix.

Local and Railway database majors are currently different. Local PostgreSQL 17
volumes were deliberately preserved, not attached to a PostgreSQL 18 image.
Aligning local runtime to 18 needs a separate approved backup/restore migration;
never edit the Compose image and reuse an older-major data directory directly.
The release gate runs on both database majors during this transitional state.

## Verification

`./mvnw --batch-mode clean verify` rebuilds from clean artifacts and runs the
complete quality gate. Result: **135 tests, zero failures/errors/skips**.
Six inherited data-bearing feed/filter/detail tests execute on PostgreSQL 18.6
in addition to the H2 suite; this includes default-null filters, individual
optional filters, accent-insensitive search and pagination.

The production Docker image is built from the release worktree. Release startup
verification restores the actual Railway V9 custom-format dump into a fresh,
temporary PostgreSQL 18.6 container. Synthetic buyer/merchant fixtures are added
only to that scratch database to check preservation across V10-V14. No migration
file V1-V14 is modified; Railway itself remains untouched until the PR is merged.

Observed scratch startup results:

- Original V1-V9 checksums validate; all five forward migrations V10-V14 succeed.
- Hibernate schema validation succeeds and health reports UP.
- Existing synthetic merchant profile and BUYER/MERCHANT roles are preserved.
- OpenAPI JSON returns HTTP 200 with 29 paths; public default-filter feed returns
  HTTP 200 instead of the previous PostgreSQL nullable-parameter error.
- Restart validates V14 again without rerunning migrations; health returns UP.
- No PostgreSQL-18/Flyway unsupported-version warning remains.
- Temporary containers, network and scratch volumes are removed after checks;
  existing local containers, data volumes and the original portable dump remain.

The original portable backup and its checksum/restore-drill metadata remain

## Deployment and remaining limits

1. Review the PR and wait for CI on its newest commit.
2. Confirm Railway backend variables include database/Redis connectivity,
   JWT and OTP secrets, production CORS origins, and required external-provider
   credentials. Startup tests use dummy local mail/Cloudinary configuration and
   do not prove real email, media upload, or Google/Apple credentials work.
3. Merge using **Create a merge commit**. This triggers the configured Railway
   deployment; creating/updating a PR alone does not deploy the backend.
4. Check Flyway reports V9 -> V14, Hibernate schema validation succeeds, and
   backend health is UP. Smoke-test public feed and authentication afterward.
5. Sync release-only fixes from main back into dev with a history-preserving
   merge so future feature branches receive the same Flyway/query fixes.

Database rollback is not the same as binary rollback. An old binary with only
V1-V9 may reject already-applied V10-V14 during Flyway validation. Recovery must
coordinate the compatible binary and database snapshot; do not repair checksums,
edit applied migrations, disable validation or overwrite production blindly.

Production capacity is **not proven**: no load profile or production-like load
test was supplied. Existing feed logic still materializes and sorts all
geographic candidates before pagination, which needs bounded database-side
queries and capacity testing before high-traffic use. The release verifies
functional correctness and startup compatibility, not unlimited scalability.
